## 1. 为什么需要这份手册

img2threejs 不是神经网络直接把二维图片变成网格的“一键生成器”。
它让 Agent 根据参考图分析结构，再用 TypeScript 与 Three.js 编写
程序化几何，通过浏览器渲染和视觉反馈逐轮修正。

这种方式具有可读、可改、可交互、可动画的优势，但也容易出现一种
特殊失控：

```text
原本只需要一个可旋转的产品模型
  -> 自动升级成完整资产工程
  -> 先写巨型 spec
  -> 构建全部 sockets / colliders / 状态
  -> 每个数值微调都跑完整门禁
  -> 自动指标通过
  -> 静帧仍明显不像
  -> 仍然先导出视频
  -> 用户否决后从头返工
```

这不是“质量要求高”的必然代价，而是路线、验收顺序和资源预算错误。

本手册的目标不是降低质量，而是让每一级质量只承担必要成本：

- 快速原型要尽快得到可见反馈；
- 产品转台要先证明静态外观，再生成视频；
- 动作就绪资产才进入完整 staged pipeline；
- 透明、自由曲面和不可见结构要先证明 Three.js 路线适配；
- 同一问题重复失败时必须换方法，不能无限微调。

工具可调用、Python/TypeScript 无报错、Vite build 成功、WebGL 页面
打开、自动分数高、MP4 能播放，都不等于参考匹配成功。

## 2. 先判断 img2threejs 在本次任务中的角色

每次开始前必须回答：

> 用户最终消费的是快速可视化、参考匹配的转台画面，还是可继续开发的
> 动作就绪程序化资产？

依据答案选择一条主路线：

| 路线 | 最终消费者 | img2threejs 的责任 | 默认质量上限 |
| --- | --- | --- | --- |
| `DIAGNOSTIC_ONLY` | 人或后续执行者 | 读取、定位、解释 | 不产生修改 |
| `TOOLCHAIN_MAINTENANCE` | Codex/开发者 | 版本、安装、控制、健康 | 工具可用，不证明模型 |
| `RAPID_VISUAL_PROTOTYPE` | 用户、导演、探索者 | 快速外形与交互判断 | 可识别候选，不是正式资产 |
| `REFERENCE_MATCHED_TURNTABLE` | 审片者、营销视频 | 可见身份与转台画面 | 经批准的参考匹配候选 |
| `ACTION_READY_PROCEDURAL_ASSET` | 开发、游戏、互动、动画 | 完整程序化资产与运行时层级 | 原 Skill 全流程能力 |

### 最小充分负担原则

选择能满足真实交付的最低路线。

- “先快速看看效果”默认 `RAPID_VISUAL_PROTOTYPE`；
- “做一个像参考图的产品旋转视频”默认
  `REFERENCE_MATCHED_TURNTABLE`；
- “盖子、机械件、附件需要真实父子层级并供后续交互”默认
  `ACTION_READY_PROCEDURAL_ASSET`；
- “为什么失败、版本是什么、安装是否正常”根据是否允许修改选择
  `DIAGNOSTIC_ONLY` 或 `TOOLCHAIN_MAINTENANCE`。

不得因为底层 Skill 支持 sockets、colliders、destruction groups、
多状态和完整八阶段流程，就自动给所有任务增加这些内容。

### 最高下游负担只作用于对应产物

一个请求可以同时包含安装和建模，也可以先快速预览再升级正式资产。
必须分段应用路线：

1. 工具链部分接受 `TOOLCHAIN_MAINTENANCE`；
2. 视觉原型部分接受 `RAPID_VISUAL_PROTOTYPE`；
3. 只有用户或监督者决定升级时，才建立新的
   `ACTION_READY_PROCEDURAL_ASSET` 合同。

不得让一个最终只需转台视频的任务继承游戏资产、破坏系统或完整物理
交互的验收负担。

## 3. 五条执行路线

### 3.1 `DIAGNOSTIC_ONLY`

用于：

- 读取失败模型、代码、spec、日志、截图和浏览器状态；
- 判断为什么慢、为什么不像、为什么构建失败；
- 检查参考覆盖、方法适配和遗留风险；
- 在用户未授权修复时只解释根因。

允许进行不会改变状态的版本、文件、结构、运行时和截图检查。

不授权：

- 修改代码或 spec；
- 启动新的重建；
- 安装、升级或删除版本；
- 覆盖证据；
- 导出视频。

### 3.2 `TOOLCHAIN_MAINTENANCE`

用于：

- 安装、更新、固定、删除或回滚 img2threejs；
- 核对官方仓库、tag、commit、license 和依赖；
- 验证 Codex 可发现 Skill；
- 建立 start、stop、health、preview 或等价控制入口；
- 运行最小工具链 smoke test。

工具链健康不证明任何具体模型已完成。安装任务不得因为“顺便验证”
而擅自上传、转换或长期保存用户参考图。

### 3.3 `RAPID_VISUAL_PROTOTYPE`

用于：

- 快速判断某张图能否转成有体积的 Three.js 模型；
- 快速制作可旋转、可观察的产品或道具候选；
- 在决定是否投入完整程序化重建前验证方法；
- 为创意或镜头讨论提供粗略 3D。

默认只实现：

- 主体轮廓；
- 主要组件关系；
- 1–3 个身份级材质区域；
- 必要的一个活动枢轴；
- OrbitControls 或等价浏览器查看。

默认不实现：

- 完整 sockets、colliders、destruction groups；
- 与当前展示无关的隐藏结构；
- 完整 PBR 证据提取；
- 大型 detail inventory；
- 全部互动状态；
- 最终视频。

终态必须明确为原型或候选，不能写成正式参考匹配或动作就绪资产。

### 3.4 `REFERENCE_MATCHED_TURNTABLE`

用于：

- 产品、包装、道具的 360° 或有界旋转展示；
- 需要与参考图在可见结构、比例、标签和材质上相似；
- 需要少量开合、附件或可见内部状态；
- 最终目标是静帧或视频展示，而不是游戏/工程资产。

只构建转台实际需要的内容：

- 镜头可见主体结构；
- 转动时会暴露的四周轮廓；
- 参考明确的开合或附件层级；
- 对身份有影响的标签、文字和材质分区；
- 一个独立的捕获旋转根，不破坏模型内部枢轴。

不得用运动模糊、快速旋转、景深或挑选角度掩盖静态造型失败。

### 3.5 `ACTION_READY_PROCEDURAL_ASSET`

用于：

- 游戏、交互、动画、拆装或运行时状态；
- 确实需要层级、sockets、colliders、attachments、detachable groups；
- 需要底层正式 img2threejs staged pipeline；
- 需要其他开发者继续维护程序化源代码。

该路线读取并执行已安装版本的完整 img2threejs Skill，包括其 intake、
pre-spec、strict validation、locked passes、comparison review 和
bounded correction loop。

完整流水线不代表无限资源。仍必须遵守本手册的最早视觉门、同缺陷
两轮停止门、稳定检查点验证和人工视觉否决优先。

### 合同变更

以下变化必须重新路由，不得静默发生：

- 从快速原型升级为参考匹配；
- 从转台升级为动作就绪资产；
- 新增隐藏结构精确要求；
- 新增透明、液体、布料、毛发或自由曲面高保真要求；
- 新增开合、拆装、碰撞或游戏运行时要求；
- 时间预算、修正循环或证据预算超过上限。

路线升级必须说明新增价值、成本、风险和对现有检查点的影响。

## 5. 方法适配门

img2threejs 的核心是 reconstruction-by-code。先判断目标是否适合
程序化 Three.js，而不是看到参考图就承诺。

### 5.1 绿色：默认适配

- 不透明或材质分区清晰的硬表面；
- 主要由 lathe、box、cylinder、extrude、curve、tube 等可解释几何构成；
- 对称或制造逻辑明确；
- 有清晰正面与至少一个非退化侧面/三分之四视角；
- 隐藏面允许合理近似；
- 输出目标是实时浏览器模型。

### 5.2 黄色：先做限时可行性样片

- 厚壁透明、半透明、强折射或镜面产品；
- 乳霜、液体、泡沫、布料、毛发、植物等自由曲面；
- 多个参考图的相机、姿态、开合和灯光不一致；
- 精确品牌文字沿曲面排布；
- 需要多个机械状态但缺少内部结构证据；
- 参考中的外观高度依赖摄影灯光和后期。

黄色目标先进入限时原型。只证明关键难点，不得先建设完整资产。

### 5.3 红色：纯程序化路线不得默认承诺

- 要求不可见背面、内部或连接结构一模一样，但没有证据；
- 要求 CAD、制造、公差、物理折射或真实流体级准确；
- 要求从未校准的多张照片恢复精确多视图几何；
- 同一身份缺陷连续两轮仍没有收敛；
- 参考匹配必须依赖真实扫描、复杂贴图投影或 DCC 雕刻；
- 用户要求广告最终像素，但 Three.js 仅能提供近似。

红色目标应选择以下之一：

- 请求更多正交视图、尺寸、CAD、贴图或产品资料；
- 明确接受近似并降低路线；
- 切换 Blender、摄影测量、神经重建、投影或混合工作流；
- 返回 `blocked_method_mismatch`。

“继续调一点参数”不是红色目标的解决方案。

## 6. 所有路线共享的启动门

### 6.1 目标门

记录：

- 用户真正需要的产物；
- 是否只需浏览器预览、静帧、视频或可开发资产；
- 必须像的身份级特征；
- 允许近似的区域；
- 最终可见状态和视角；
- 指定视觉审批者；
- 完成定义。

### 6.2 来源门

建立参考角色：

```text
尺寸/CAD/真实源模型
  > 经批准的正交或多角度产品图
  > 当前产品摄影图
  > 同系列结构参考
  > 生成图或文字推测
```

不同照片的构图、姿态、开合和光线不一致时，不得把它们冒充已校准的
多视图数据集。每张图必须声明用途，例如：

- 正面比例；
- 开盖层级；
- 三分之四空间关系；
- 顶视轮廓；
- 材质高光参考。

### 6.3 版本与环境门

现场验证：

- 安装路径；
- 版本、tag、commit 和 license；
- Python、Node、npm、Three.js、TypeScript 和 Vite；
- Browser/preview 控制是否真实可用；
- start、stop、health、冷启动和端口归属；
- 当前工作目录和输出目录；
- 是否存在旧版本或被拒绝基线。

旧记忆只能定位检查项，不能代替本次现场状态。

### 6.4 非破坏门

- 原始参考保持只读；
- 新版本使用独立目录或明确版本后缀；
- 被拒绝的 V1/V2 不得覆盖、删除或重写；
- 每个稳定检查点记录源文件、截图和状态；
- 任何视频、证据或报告都必须绑定具体模型快照。

### 6.5 预算门

在执行前确定：

- 首张视觉检查点的期限；
- 总时间预算；
- 最大视觉修正循环；
- 最大完整验证次数；
- 最大证据规模；
- 超限后的停止或换路线动作。

预算不是完成承诺，而是强制重新决策点。

## 7. 路线 A：只读诊断

流程：

```text
确认只读范围
  -> 读取版本/代码/spec/日志/截图
  -> 区分工具、运行时、视觉和流程问题
  -> 定位根因
  -> 给出修复或换路线选项
  -> 停止
```

诊断时分别报告：

- 实际命令耗时；
- Agent 推理与工具调用耗时；
- 浏览器/渲染耗时；
- 文件和证据规模；
- 视觉循环数量；
- 任务是否发生静默范围升级；
- 自动指标是否与人工观感冲突。

不得用“对象复杂”解释所有异常时长。若 build 只需数秒而任务运行数小时，
主要问题通常在调度、证据风暴或修正循环。

## 8. 路线 B：工具链维护

流程：

```text
官方来源核验
  -> 本机只读 preflight
  -> 精确版本安装或修改
  -> Codex discovery
  -> start/stop/health
  -> 最小真实 smoke
  -> 冷启动复验
  -> 版本与限制报告
```

要求：

- 不把 mutable `main` 冒充 release；
- 不把不存在或未正式发布的版本写成已安装；
- 不破坏性升级全局 Python、Node、CUDA 或其他工具；
- 不以 HTTP 200 代替 WebGL 页面和控制验证；
- 不因维护任务自动处理用户产品图；
- 版本删除必须核对精确目标和残留入口。

## 9. 路线 C：快速视觉原型

默认预算：

| 项目 | 默认值 |
| --- | --- |
| 首个可辨认浏览器检查点 | 15 分钟内 |
| 总预算 | 30 分钟 |
| 硬复审点 | 45 分钟 |
| 最大视觉修正循环 | 2 |
| 完整 typecheck/build | 稳定终点 1 次 |
| 正式对比图 | 1–2 张 |
| 截图总量 | 不超过 6 张 |

流程：

```text
最少目标合同
  -> 参考角色与方法适配
  -> 主轮廓/主组件 blockout
  -> Browser 固定视角 + 一个 orbit 视角
  -> 视觉判断
  -> 最多两轮有界修正
  -> 稳定后一次 typecheck/build
  -> 原型候选或停止
```

第一张图必须能够回答：

- 主体是否一眼可识别；
- 总高宽、主轮廓和主要部件比例是否合理；
- 物体是否具有真实体积而非平面伪装；
- 最难材质或自由曲面是否有可行路径。

若首个检查点已显示方法不适配，立即停止或换路线。不得用完整 spec、
完整材质和交互系统来“挽救”错误 blockout。

## 10. 路线 D：参考匹配转台

默认预算：

| 项目 | 默认值 |
| --- | --- |
| 首个轮廓检查点 | 20 分钟内 |
| 总预算 | 60 分钟 |
| 硬复审点 | 90 分钟 |
| 最大视觉修正循环 | 3 |
| 同一缺陷参数修正上限 | 2 轮 |
| 完整验证 | 最多 2 套 |
| 诊断截图 | 不超过 12 张 |
| 最终对比 | 2–5 张，按适用视角 |

流程：

```text
身份与可见状态合同
  -> 方法适配样片
  -> 轮廓/比例/组件关系
  -> 代表静帧门
  -> 材质与标签
  -> 代表静帧复审
  -> 稳定快照完整验证
  -> 指定审批者决定
  -> 解锁视频
  -> 视频技术与视觉 QA
```

### 10.1 代表静帧

按产品选择最小覆盖集：

- 闭合正面；
- Hero 三分之四；
- 转台会暴露的背面或侧面；
- 透明、内胆或开合产品的打开状态；
- 透明/反射/自由曲面产品的顶视或 grazing view。

参考与渲染对比必须：

- 真实 50/50；
- 同尺度、同方向和可解释的相机匹配；
- 无浏览器 UI；
- 不裁掉失败区域；
- 同时保留至少一个非有利 orbit 视角。

### 10.2 转台最小资产

只实现：

- 旋转会看到的表面；
- 参考证实的开合和附件；
- 捕获旋转根；
- 稳定相机、灯光和背景；
- 必要标签。

除非请求需要，不增加碰撞体、破坏组、游戏状态和完整 runtime API。

## 11. 路线 E：动作就绪程序化资产

开始前必须额外明确：

- 下游开发框架；
- 真实需要的动作与状态；
- 父子层级、局部坐标和枢轴；
- sockets、colliders、attachments 和 detachable groups；
- 性能预算；
- 代码交接和测试要求。

流程沿用安装版本的正式 img2threejs Skill，但增加：

1. 30 分钟内必须产生第一个真实 blockout；
2. 每 45 分钟记录一次监督检查点；
3. 同一身份缺陷两轮不收敛必须路线复审；
4. 完整门禁只运行于稳定 pass；
5. 不得让 interaction/optimization 掩盖 form/material FAIL；
6. 最终仍需人工可见审查。

完整 spec、detail inventory 和运行时结构只有在该路线中默认合理。

## 12. 最早视觉门与持续自检

### 12.1 最早视觉门

在以下工作之前必须出现可辨认的 Browser blockout：

- 扩展非身份级微细节；
- 批量 PBR crop 或纹理证据；
- 完整 interaction/state machine；
- colliders、destruction groups；
- optimization；
- presentation composer；
- 视频导出。

若 blockout 的轮廓、比例或组件关系失败，下一动作只能是：

- `refine-spec`；
- `refine-code`；
- `request-input`；
- `switch-method`；
- `stop`。

不得继续 material、lighting 或 animation pass。

### 12.2 Maker–Checker

每轮稳定检查点记录：

1. 当前截图或比较图；
2. 与目标的三个最大可见差异；
3. 根因假设；
4. 本轮只允许修改的问题簇；
5. 修改前后证据；
6. 对其他已通过区域的回归；
7. 结果和下一动作。

一轮只解决一个可解释问题簇，例如：

- 主轮廓/比例；
- 透明层级；
- 自由曲面形态；
- 附件父子关系；
- 标签与文字；
- 相机/灯光。

同时大改所有系统会失去因果证据。

## 13. 时间、循环与证据熔断

### 13.1 同缺陷两轮停止门

同一身份级缺陷连续两轮仍失败时：

1. 冻结当前最好版本；
2. 停止第三轮纯参数微调；
3. 判断是 spec 错、几何架构错、材质/灯光错、参考不足还是方法不适配；
4. 只有提出新的架构或证据假设后才允许第三轮；
5. 否则切换方法或返回阻塞。

### 13.2 其他强制停止条件

- 输出在两个版本间来回振荡；
- 自动分数提高但人工观感不提高；
- 同一组脚本和截图被重复生成；
- 超过 20 次 Browser/MCP 操作仍无新稳定视觉检查点；
- 超过 15 分钟没有新的可见证据；
- 上下文压缩后开始重做已验证工作；
- 预算到达硬复审点；
- 用户或指定审批者明确否决。

### 13.3 证据预算

快速和转台路线遵循证据经济原则：

- 调参过程不为每个数值保存一套日志；
- 只保存稳定检查点和被拒绝基线；
- 同一稳定快照只需要一套 normal/strict/typecheck/build 证据；
- 不创建与交付无关的数百张 crop、overlay 或截图；
- 不允许 spec 规模远超实际组件而没有路线理由。

超出预算时先说明新增证据将解决什么不确定性。不能回答时不得扩展。

## 14. 浏览器实时调参与正式验证

Three.js 的优势是实时交互。应利用它，而不是每次修改一个浮点数后
重新执行完整生产门禁。

推荐循环：

```text
稳定源码
  -> Vite hot reload / 临时 debug controls
  -> 连续调整高杠杆参数
  -> Browser 固定相机观察
  -> 选择一组稳定值
  -> 落盘并同步 spec
  -> 再运行正式验证
```

适合实时调节：

- 主尺度与比例；
- lathe profile；
- 透明度、transmission、IOR、thickness、roughness；
- 灯光位置、强度与环境；
- 自由曲面峰值、宽度、偏心和扫痕；
- lid/attachment presentation；
- 相机焦段、距离和目标点。

临时调参 UI 必须：

- 只在 debug 模式出现；
- 不污染最终截图；
- 稳定后把值写回源代码和 spec；
- 最终验收前关闭或隐藏。

### 正式验证时机

- 第一个可运行里程碑：一次 typecheck/build；
- 每个稳定候选：按路线决定是否运行；
- 最终快照：必须运行；
- 单个材质或几何数值微调：不需要完整四门禁。

若源代码或 spec 在门禁后又发生变化，旧门禁立即失效。

## 15. 静帧先于视频

视频始终默认锁定。

解锁条件：

1. 路线合同声明代表视角；
2. 所有代表静帧属于同一稳定模型快照；
3. 比较图满足同尺度、同方向、无 UI；
4. 身份级特征无人工硬失败；
5. 指定视觉审批者明确放行；
6. 对应快照的正式验证通过。

静帧未通过时禁止：

- 输出“最终”MP4；
- 用快速旋转隐藏侧面问题；
- 用景深遮挡错误；
- 用运动模糊弱化轮廓；
- 只展示最好看的正面；
- 用视频技术指标证明模型外观。

### 视频验收

静帧通过后仍要单独检查：

- 分辨率、帧率、时长、编码、色彩和音频要求；
- 帧数、重复/缺失帧；
- loop 连续性；
- 相机和旋转根是否污染模型内部层级；
- 转动中全部方位的轮廓、标签和材质；
- 打开/隐藏状态是否需要独立证据。

闭合转台不能证明被遮挡的内部结构。

## 16. 自动指标与人工视觉的边界

### 16.1 自动指标能证明什么

- schema 与 spec 结构；
- TypeScript 和 build；
- 页面/运行时状态；
- 可重复尺寸、覆盖、轮廓、色差或性能测量；
- 视频编码和帧级技术事实。

### 16.2 自动指标不能单独证明什么

- 产品是否“一眼像”；
- 透明材质是否具有可信厚度；
- 自由曲面是否自然；
- 机械关系是否符合真实产品；
- 标签和字体是否保持品牌身份；
- 画面是否达到广告或审美标准。

规则：

```text
自动 FAIL 可以阻断
人工视觉 FAIL 必须阻断
自动 PASS 不能推翻人工视觉 FAIL
```

指标只有在参考与渲染可比较时才有效。相机、尺度、裁切、姿态或状态
不一致时，IoU、SSIM、色差和覆盖率不得用于晋级。

## 17. 线程、Worker 与多 Agent 规则

### 17.1 单写者

- 一个 Worker 写模型和 spec；
- 一个独立 Checker 只读审片；
- 监督线程决定路线、预算、视觉放行和是否换方法；
- 其他 Agent 只能做只读测量、来源或风险检查。

不得让多个 Agent 同时修改同一 `model.ts`、spec 或证据目录。

### 17.2 临时线程

临时 Worker 必须：

- 属于当前真实项目；
- 使用正确 cwd；
- 可见、未置顶、未归档；
- 不修改长期 SSOT；
- 每个稳定检查点报告产物、状态、预算和下一动作；
- 结束时记录 handoff，而不是只写“完成”。

### 17.3 监督节奏

- Worker 活跃时，监督者优先读取检查点，不做重复全量读取；
- 追加要求应在消息边界或检查点下发；
- 避免连续微提示把当前 turn 打断成多轮；
- 上下文压缩或流断开后从第一个未验证项恢复；
- 不重做已验证产物；
- 超过预算而无视觉进展时，监督者必须暂停并重新路由。

任务调用数量、修改数量和日志数量不是进度。只有新的稳定可见证据才是。

## 18. 版本、来源与安全

- 使用精确安装路径、tag 和 commit；
- 安装与项目输出分离；
- 不修改第三方 versioned source 来保存本机治理规则；
- 本手册属于全局治理层，底层正式 Skill 仍是版本行为权威；
- 参考图默认留在本机，不向外部服务上传；
- 不执行未经检查的第三方脚本；
- 不破坏性升级全局环境；
- 删除版本前核对 discovery、source、work、logs 和控制入口；
- 所有输出使用绝对路径和明确版本。

## 19. 五条独立验收轴

每次交付分别报告：

### A. 来源与方法适配

- 参考是否足够；
- 未见区域如何处理；
- 程序化 Three.js 是否适配目标；
- 是否需要换 Blender、投影或其他路线。

### B. 结构与运行时

- 组件、层级、局部变换、枢轴、状态和附件；
- 是否只做了画面伪装；
- Browser 交互是否真实工作。

### C. 视觉身份

- 轮廓、比例、材料分区、标签、文字、透明层级和自由曲面；
- 是否有合格比较图；
- 指定视觉审批者是否接受。

### D. 工程与性能

- spec、源码、typecheck、build、浏览器错误、三角形、draw calls；
- 是否可冷启动、可恢复、可移交；
- 性能结论是否来自目标硬件。

### E. 下游交付

- 静帧、视频或资产的格式与消费者是否匹配；
- 视频技术 QA；
- 是否把上游候选误报成最终批准。

每轴使用 `pass`、`partial`、`blocked` 或 `not_applicable`。不得以一轴
的 PASS 覆盖其他轴。

## 21. 禁止的捷径

- 不得把“给我一个旋转视频”升级成完整游戏资产。
- 不得在第一个可辨认 blockout 前建设巨型 spec 和证据库。
- 不得把 build、strict、IoU、色差或 runtime PASS 当作视觉 PASS。
- 不得用自动分数推翻用户或指定审批者的视觉否决。
- 不得在代表静帧失败时导出最终视频。
- 不得用运动、景深、模糊或挑选角度隐藏模型问题。
- 不得让同一缺陷进行第三轮无新假设的参数微调。
- 不得每改一个数值就运行完整门禁。
- 不得用数百张截图、日志和 crop 冒充进度。
- 不得把不同姿态、不同相机的照片冒充校准多视图。
- 不得发明不可见背面、内部和机械连接。
- 不得让多个 Agent 同时写同一模型。
- 不得覆盖被拒绝基线。
- 不得把快速原型称为参考匹配资产。
- 不得把可播放 MP4 称为已批准视频。
- 不得把本机受限 Browser 的帧率冒充目标 GPU 性能。
- 不得在方法已经不适配时继续无限消耗。

最终原则：

> img2threejs 的价值是快速把可解释结构写成可交互的 Three.js 代码，
> 不是把每张图片都拖入完整资产工程。先选择交付路线，尽早看真实画面，
> 只在稳定检查点验证；自动指标不能覆盖人工视觉，静帧不过不做视频，
> 同一问题两轮不收敛就换假设或换方法。
